# Combat Mechanics 3.0

## 1. Overview & Core Principles

This document outlines a revised architecture for combat mechanics within the D&D 5e game rule plugin. The primary goal is to create a robust, consistent, and predictable combat system by removing non-deterministic elements from core logic.

The guiding principle is a strict adherence to the **Interpreter-Engine-Narrator (IEN)** model:

*   **Interpreter (LLM):** Used exclusively to translate player's natural language commands into structured, machine-readable data.
*   **Engine (Plugin):** The sole authority for all game rules, state management, and decision-making. All calculations, rolls, and outcomes are handled programmatically within the plugin.
*   **Narrator (LLM):** Used exclusively to describe the factual outcomes generated by the Engine in engaging prose.

Under this model, the LLM is never asked to make a decision, count objects, or determine the flow of events.

## 2. Combat Initiation Flow

Combat begins when a trigger event occurs. The subsequent flow is handled entirely by the programmatic Engine.

### 2.1. Combat Triggers

There are two primary triggers for combat:

1.  **Narrative-Driven:** An event in the story initiates combat (e.g., an ambush, a monster revealing itself).
2.  **Player-Driven:** The player character initiates hostilities (e.g., launching an attack, successfully provoking an enemy).

### 2.2. The `initiative_triggered` Event

Both trigger types will result in an `initiative_triggered` event being processed by the plugin's `handleConsequence` function. This is the single entry point for starting a battle, which executes the following steps:

1.  **Programmatic Encounter Generation:**
    *   The Engine identifies the current environment (e.g., "forest", "dungeon") from the game state.
    *   It consults a new, local data source: `encounterTables.ts`.
    *   It programmatically rolls to determine the **exact type and quantity** of monsters, completely removing the LLM from this decision.

2.  **Initiative and Turn Order:**
    *   The Engine rolls a `d20` + dexterity modifier for the player and a `d20` for each NPC.
    *   A static turn order for the entire duration of the combat is created and stored in the battle state.

## 3. The Combat Round Loop

The combat loop proceeds turn-by-turn according to the established initiative order.

### 3.1. NPC Turns: Deterministic AI

A critical change is the removal of the LLM from NPC decision-making.

*   When an NPC's turn arrives, the Engine calls a new, internal AI function.
*   This function uses a simple, hard-coded ruleset to determine the NPC's action (e.g., "If HP is below 25%, attempt to use a healing item or disengage. Otherwise, attack the closest enemy.").
*   The chosen action is resolved programmatically by the Engine. This ensures NPCs behave consistently and tactically, based on predefined logic.

### 3.2. Player Turn: Pause, Interpret, Resume

The loop is designed to be interactive and responsive to player input.

1.  **Pause:** When the player's turn is reached in the initiative order, the Engine pauses the combat loop.
2.  **Present Actions:** The system presents the player with a list of available actions (e.g., Attack, Cast Spell, Use Item).
3.  **Await Input:** The Engine waits for the player to submit their action in natural language.
4.  **Interpret:** The player's input string is sent to the generic **Interpreter** service, which uses the LLM to convert it into a structured command (e.g., `{ action: 'Attack', target: 'Goblin 2' }`).
5.  **Resume and Resolve:** The Engine receives this structured command, validates it, and resolves the action's outcome. It then resumes the combat loop, executing the turns for any remaining NPCs in the round.

This cycle repeats until a combat end-condition is met.

## 4. State Management & Time Tracking

### 4.1. Deterministic Time

To solve temporal inconsistencies, time is now tracked programmatically.

*   A new property, `gameTimeInSeconds`, will be maintained in the plugin's state.
*   Each completed combat round will advance this clock by a fixed amount (**6 seconds**), corresponding to D&D 5e rules.
*   Non-combat actions (e.g., searching a room) will also have a fixed time cost that is added to the clock when they are performed.

### 4.2. State Authority

The plugin's Engine is the absolute source of truth. All changes to game state—including character HP, status effects, inventory, and the game clock—are mutated directly and only by the Engine's programmatic functions.

## 5. Narration

Combat narration is handled by a distinct and separate flow.

*   After a full combat round is completed (player and all NPC turns), the Engine compiles a **structured report** of all events that occurred (e.g., who attacked whom, the damage dealt, who was defeated).
*   This factual report is sent to a specific **Combat Narrator** prompt (`getCombatRoundNarrationPrompt`).
*   The Narrator LLM's only job is to turn this list of facts into an exciting narrative. It does not add, remove, or change any of the outcomes.

## 6. Summary of Benefits

*   **Consistency:** Encounters, NPC behavior, and time progression are predictable and rule-based.
*   **Reliability:** The system is no longer subject to the creative whims of the LLM for critical game mechanics.
*   **Testability:** The programmatic Engine, including encounter generation and NPC AI, can be unit-tested.
*   **Performance & Cost:** Reduces LLM calls and complexity during the combat loop, leading to faster and more efficient execution.

## 7. Implementation Impact Analysis

This section details the specific files within the `game-rule-dnd5e` plugin that will be modified to implement the Combat Mechanics 3.0 system. The changes are designed to be concentrated within the plugin, leaving the main application framework untouched.

### `plugins/game-rule-dnd5e/src/encounterTables.ts`

*   **Change Type:** New File
*   **Summary of Changes:** This new file will be created to house the static, programmatic encounter tables. It will export a mapping of environment types (e.g., 'forest', 'dungeon') to weighted lists of possible monster encounters. Each entry will define the monster type and a dice string for its quantity (e.g., `{ monster: 'Goblin', quantity: '2d4' }`). This file becomes the single, deterministic source of truth for encounter generation.

### `plugins/game-rule-dnd5e/src/main.tsx`

*   **Change Type:** Major Refactoring
*   **Summary of Changes:** This file requires the most significant changes to integrate the new logic:
    *   **`handleConsequence` function:** The logic for the `initiative_triggered` event will be completely rewritten. The LLM call to determine enemy counts will be removed. It will be replaced with new logic that imports from `encounterTables.ts`, identifies the current environment, and programmatically rolls for the encounter.
    *   **`executeCombatRound` function:** This function will be refactored to remove the LLM call for determining NPC actions. It will instead call a new, internal, deterministic AI function (`_getNpcAction`) that contains the rule-based logic for NPC behavior. The time tracking logic will also be added here, incrementing the game clock by 6 seconds after each completed round.
    *   **`resolveCheck` / `handleConsequence` functions:** These will be reviewed and updated to add appropriate time costs for non-combat actions (e.g., 'Search', 'Rest') to ensure consistent time progression outside of combat.

### `plugins/game-rule-dnd5e/src/pluginData.ts`

*   **Change Type:** Minor Addition
*   **Summary of Changes:** The core state schema for the plugin, `DnDStatsSchema`, will be updated to include a new property: `gameTimeInSeconds: number`. This will serve as the official in-game clock, managed exclusively by the plugin's engine.
